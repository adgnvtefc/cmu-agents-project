# Distill the demos, then sharpen decisions

C3 trails demos-in-prompt because of what it is trained on, not because the adapter is too small or the learning rate too low. Each per-(user, skill) adapter sees roughly **15 preference-critical training states**. Each of those is decided by one or two tokens, about 1% of the supervised tokens. The adapter is never trained on the off-path states it reaches at test time. The approach with the largest expected effect is **DAgger-style context distillation**: the frozen base model with the user's five demos in its prompt (the C1 arm, 9/9 on preference-critical steps) labels new synthetic task instances and the states the student adapter actually visits, and the adapter is trained on those labels. In the closest published analogue, distillation recovered **27.9 of a teacher's 28.2 points, where fine-tuning on the same eight examples reached 18.9** ([Snell et al.](https://ar5iv.labs.arxiv.org/html/2209.15189)). It is also the most expensive option, at about 12–16 engineering hours and 3.5–5 Mac-hours per (user, skill). The cheapest gains come from changing the supervision itself: thoughts that state a habit mined from the demos plus the task's progress, upsampling the user's distinctive steps, and a loss that weights decision tokens. In the current templates those tokens sit in the Thought's quoted element name, not in the Action span that the existing weighted-loss patch targets. Contrastive DPO against other users' aligned actions helps only when it is gated to critical states and anchored: in the one matching GUI study, vanilla DPO on persona pairs *lowered* compliance below SFT ([TIPO](https://arxiv.org/html/2604.11259)). An OPPU-style warm start from other users' skill adapter is nearly free and mainly buys procedure and stability. The deployment constraint has one sharp consequence. With only persona-independent task checks, outcome-filtered self-training cannot tell skipping the user's steps from doing them, and C3's own runs (2/3 task success, 0/3 with all preferences) show it would reinforce the failure. Every preference signal must therefore come from demos. With 9 critical test steps per adapter (±30 points), no claim is possible until results are pooled across all 12 adapters.

## Fifteen states and two tokens carry each adapter's preferences

The arithmetic of the dry run explains most of C3's behaviour. Five demos give about 70 step samples, and 9 of 42 test steps (21%) are preference-critical, so an adapter trains on roughly 15 states where this user's action differs from every other user's (my estimate from the test split). In UI-TARS output the action is decided by one or two tokens. An adapter at a mean loss of 0.16 **still picked the wrong action on 10 of 15 training steps, with the decision tokens at 2–2.5 nats** ([STATUS.md](/Users/hanmozhang/schoolwork/cmu-agents-project/STATUS.md)). At about 40 supervised tokens per sample, the decision tokens on critical states are on the order of 30 of ~2,800 supervised tokens, about 1% of the loss mass (my estimate). Mean cross-entropy converges on boilerplate, and a falling loss curve says nothing about whether the adapter has learned the user.

The templates decide where the decision actually lives. Every recorded step gets a deterministic thought built from its target element: a click becomes `Next, I'll click "30 min".` and a typed value becomes `I'll type "14:00" into the Start time field.` ([agent/thoughts.py](/Users/hanmozhang/schoolwork/cmu-agents-project/agent/thoughts.py)). The model writes the Thought before the Action. So the first token where Alice's response differs from the skip (`"Guests"`) or from Bob's value (`"15:00"`) is the **quoted label or value inside the Thought**, and the coordinates that follow only ground a choice already made. The uncommitted A5 patch multiplies the loss by 4 from the last `Action` token onward ([train/weighted_sft.py](/Users/hanmozhang/schoolwork/cmu-agents-project/train/weighted_sft.py)). As written, it strengthens grounding after the decision and leaves the decision token at weight 1. Fixing that takes about an hour and should happen before any A5 result is read.

C3's errors come in two kinds, and they need different fixes. It learned Alice's *values*: it types her 14:00 and 10:00 start times and, offline, picks her 10-minute reminder. It skips *steps* instead. Offline, it bypassed "30 min" in all three test demos, going straight to Guests and leaving the 60-minute default. Online, it skipped the 30-minute, video and reminder steps, for 40% preference adherence ([STATUS.md](/Users/hanmozhang/schoolwork/cmu-agents-project/STATUS.md)). A value step lies on the path the agent is already walking. An omission step requires leaving it, at a moment when a pre-filled default makes "move on" a valid continuation, and the template thought gives no reason to deviate. The offline/online split points to covariate shift. On demo states the adapter chooses the reminder; once it has skipped "30 min" in a live run, it is in states it never trained on and never rejoins the user's procedure. Teacher-forced SFT never shows the adapter its own off-path states. That is the premise of DAgger, which trains on learner-visited states labelled by an expert ([Ross et al.](https://arxiv.org/abs/1011.0686)).

The "repeat the previous action" failure has two cheap explanations to rule out before changing the model. A screenshot captured before the UI re-renders shows an unchanged screen, which makes repeating the action the rational choice. A 2026 study of long-horizon mobile agents names this failure *stale-screen repetition* ([Task-State Representation](https://arxiv.org/html/2607.00502)). The live harness waits a fixed 250 ms after each action (plus a page-load wait) but never checks that the frame actually changed ([agent/run.py](/Users/hanmozhang/schoolwork/cmu-agents-project/agent/run.py)). The recorder mis-paired frames under GPU load until it was fixed on November 21, and three oracle demos still carry flagged stale frames ([STATUS.md](/Users/hanmozhang/schoolwork/cmu-agents-project/STATUS.md)). The second explanation is that the current thoughts encode no progress: each one restates the current action, and the history the model sees is a list of such restatements. OpenCUA found that **thought history gave no benefit over action-only history** at 3 screenshots, and that a mixture of output formats in training beat a single format (18.5 vs 13.1 on OSWorld) ([OpenCUA](https://arxiv.org/html/2508.09123v3)).

The instability at lr ≥ 1e-4 fits an optimizer mechanism better than a precision one. In the installed mlx-vlm 0.8, LoRA matrices are created in fp32 and Adam state inherits the parameter dtype, so bf16 rounding of adapter updates is unlikely to be the cause ([lora_layers.py](/Users/hanmozhang/schoolwork/cmu-agents-project/.venv/lib/python3.12/site-packages/mlx_vlm/trainer/peft/lora_layers.py), [optimizers.py](/Users/hanmozhang/schoolwork/cmu-agents-project/.venv/lib/python3.12/site-packages/mlx/optimizers/optimizers.py)). The likelier mechanism runs like this. Each batch-1 sample carries about 40 supervised tokens, most near zero loss. A sample whose decision token is wrong produces a gradient far larger than Adam's running second moment, which at the default β2 of 0.999 averages over roughly 1,000 steps in a 280-step run. Wortsman et al. found that loss spikes **follow 1–8 iterations after the second-moment estimate underestimates the squared gradients** ([Wortsman et al.](https://arxiv.org/abs/2304.13013)). MLX's gradient clipping multiplies every gradient by a single normalizer, so one non-finite element turns the whole update into NaN. That matches "lr 1e-4 + grad-clip → NaN by iter 25". The installed CLI already exposes `--beta2` (default 0.999) and `--gradient-accumulation-steps` ([train.py](/Users/hanmozhang/schoolwork/cmu-agents-project/.venv/lib/python3.12/site-packages/mlx_vlm/train.py)). Capacity is not the limit. A rank-16, all-linear adapter on this 28-layer model has about 40.4M parameters, roughly 10× OPPU's per-user LoRA (computed from [config.json](/Users/hanmozhang/schoolwork/cmu-agents-project/models/UI-TARS-1.5-7B-mlx-bf16/config.json)). And LoRA variants land within 1–2% of each other once the learning rate is tuned ([Lee et al.](https://arxiv.org/abs/2602.04998)). The optimal LoRA learning rate is about 10× the full fine-tuning rate, but LoRA tolerates large batches less well, and the safe rate at batch 1 is lower ([Thinking Machines](https://thinkingmachines.ai/blog/lora/)). Stability fixes therefore make higher learning rates *testable*, but they are not a cure: a higher learning rate scales boilerplate and decision gradients alike.

## Task-only checks make self-training reinforce the skips

The constraint leaves five legitimate signals, and each has a distinct job. **The user's own demos are the only preference oracle.** **Other users' demos supply contrast**: they mark which of the user's steps are distinctive, and they provide negatives. **The base model with the user's demos in its prompt is a teacher** that already scores 9/9 offline. **The environment** supplies new states, resets, and per-frame element maps for snapping clicks to real targets. **Persona-independent checks** verify task facts (right attendee, right date, event saved) and collateral damage. The project's checker already returns `success` and `collateral` separately from `prefs` ([apps/checkers.py](/Users/hanmozhang/schoolwork/cmu-agents-project/apps/checkers.py)), so the allowed part is easy to isolate.

The consequence is that **a checker that cannot see preferences cannot see skipping**. C3's online runs passed the task check in 2 of 3 cases while meeting all preferences in 0 of 3, and they were shorter than C1's (11.0 vs 14.3 steps) ([STATUS.md](/Users/hanmozhang/schoolwork/cmu-agents-project/STATUS.md)). Rejection-sampling fine-tuning on task successes would keep exactly those skip trajectories. The "keep the shortest successful episode" heuristic in the augmentation notes would *prefer* them, and an outcome-reward RL loop would reward the shorter path. Published self-improvement gains on web agents, such as +31% on WebArena from filtered self-training and 4.8% → 42.4% with curriculum RL, rest on success signals that encode the whole task ([Patel et al.](https://arxiv.org/abs/2405.20309v2), [WebRL](https://arxiv.org/abs/2411.02337)). Under this constraint those signals are blind to preferences, so outcome-filtered methods rank last for preference learning.

Several recipes in the research notes quietly use a disallowed signal. Each has a compliant replacement:

| Research-note recipe | Disallowed signal it used | Compliant replacement |
|---|---|---|
| Rationale thoughts "generated deterministically from the persona file" | Persona card | Habits mined from the user's demos and contrasted with other users' demos (approach 4) |
| Replays and RFT episodes kept only "if task and preference checkers pass" | Preference checker | Task checker only, with no shortest-episode selection; labels come from the user's demo or the demo-conditioned teacher |
| Scripted state-conditional oracle that knows the user's preference steps; `recorder/oracle.py` | Persona card | The demo-conditioned teacher (approach 1), or replay of the user's own demo program |
| GRPO bonus on checker-marked preference steps | Preference checker | Bonus on demo-mined distinctive steps; reward is a match to the user's demo action |
| Pooled user tag "plus a one-line preference profile" | Persona card | An opaque user-ID tag only |
| DPO pair labels from "the persona checker or demo ownership" | Preference checker | Demo ownership only |
| Checker-filtered distillation and oracle relabelling | Both | Evaluation-only ceilings, never arms or filters |

Two subtler leaks need a decision too. First, the study gives every persona the same task instances ([apps/tasks.py](/Users/hanmozhang/schoolwork/cmu-agents-project/apps/tasks.py)), and the critical-step rule compares personas on the same instance ([eval/summarize.py](/Users/hanmozhang/schoolwork/cmu-agents-project/eval/summarize.py)). A deployed system would see other users' demos of the same *skill* on *different* instances. Distinctive-step mining and DPO pairing should therefore key on UI state (page, open dialog, focused field, which fields are filled) rather than on instance identity, and the paper should report both the same-instance and the cross-instance versions. Second, checkpoint and hyperparameter selection is a training signal too. Select each user's checkpoint by leave-one-demo-out accuracy on that user's five demos. Freeze recipe-level hyperparameters on the dev instances (8–13) that `apps/tasks.py` now defines. Use the preference checker only for final evaluation. Synthetic training instructions must never state a preference ("book a 30-minute meeting"). Their explicit dates, by contrast, are task facts that any task generator knows, so they are allowed.

Expectations should be calibrated first. In text personalization, adapter weights alone tie or trail context: retrieval gave **+14.92% against +1.07% for per-user PEFT** across seven LaMP tasks ([Salemi & Zamani](https://arxiv.org/html/2409.09510v2)). A per-skill LoRA lost to the same skill as in-context text on ALFWorld (45.7/50.0 vs 52.9/56.0) while halving prefill ([LatentSkill](https://arxiv.org/html/2606.06087)). The realistic target is not to beat C1. It is to match C1's preference accuracy at C3's 4,114 prompt tokens and 2.4 s per step, while keeping C3's 2/3 task success. The case for putting preferences in weights at all is that weights act at every step: appending personal history to the context mainly improves the *first* step of a trajectory ([ExpActivator](https://arxiv.org/abs/2609.33304)).

**Distillation ranks first** because it is the only compliant method that creates new decision instances at new and off-path states. On text-to-SQL with 8 in-context examples, the distilled student scored 27.9 against the teacher's 28.2 and plain fine-tuning's 18.9. The inputs were generated by the model rather than taken from the original examples ([Snell et al.](https://ar5iv.labs.arxiv.org/html/2209.15189)). Self-distillation fine-tuning on tool use reached 70.6 against 63.2 for SFT on demonstrations, with on-policy data beating offline teacher samples, which in turn beat SFT ([SDFT](https://arxiv.org/html/2601.19897)). On-policy context distillation beat the in-context teacher on multi-turn games (Sokoban 48.4 → 53.9) ([OPCD](https://arxiv.org/html/2602.12275)). Distilling a document-conditioned teacher into a LoRA beat SFT on about 10× more data ([Kujanpää et al.](https://arxiv.org/html/2412.14964v2)). In our setting the teacher labels the duration state with the "30 min" click on dozens of fresh instances, and it labels the off-path states the student reaches after a skip or a repeat. I found no GUI-agent paper that distils a user's demonstrations into weights this way (search as of November 2026), so the arm is also a contribution. Its weaknesses are cost and the teacher's ceiling. SDFT lagged plain SFT at 3B, where in-context learning was weak ([SDFT](https://arxiv.org/html/2601.19897)). C1 itself typed wrong dates for relative days, and human demos will vary more than the oracle demos that flatter C1.

**Habit and progress thoughts rank second** because they are the cheapest change to what the decision token is conditioned on. Thought content matters. Aguvis lost **11.4 points on AndroidControl low-level (80.5 → 69.1)** without its inner monologue ([Aguvis](https://arxiv.org/html/2412.04454)). UI-TARS warns that thoughts written from the gold action can match it only superficially ([UI-TARS](https://arxiv.org/html/2501.12326)), which describes today's restatement templates. Lampinen et al. showed that writing in-context inferences into the fine-tuning data closes much of in-context learning's generalization advantage ([Lampinen et al.](https://arxiv.org/html/2505.00661)). The caution is length: structured chain-of-thought trained by SFT alone dropped AITW success from 67.2 to 42.6 in GUI-Rise ([GUI-Rise](https://arxiv.org/html/2510.27210)), so these thoughts must stay to one or two short sentences. Upsampling distinctive steps follows the critical-step results: CSO supervised only about 16% of steps and still reported large gains over SFT ([CSO](https://arxiv.org/abs/2602.03412)). No paper I found tests preference-stating thoughts in GUI SFT, so this arm is new as well.

**Contrastive DPO has the most direct evidence and the most variance.** TIPO, the nearest match, uses mobile personas role-played on the same tasks with the other persona's trajectory as the negative. Vanilla DPO cut compliance from 36.86 (SFT) to 31.94, while step-gated, step-weighted DPO raised it to 46.22 ([TIPO](https://arxiv.org/html/2604.11259)). Removing the SFT anchor in Agentic-DPO cost 14–18 points, and removing the SFT warm-up left 0% ([Agentic-DPO](https://arxiv.org/html/2607.10601v1)). Our pairs are near-identical by construction, which is the worst case for likelihood displacement, where the chosen response's probability falls even as the loss improves ([Razin et al.](https://arxiv.org/abs/2410.08847)). Two facts favour mlx-vlm's DPO: it sums log-probabilities, so the shared prefix cancels and the gradient lands on the divergent tokens, and its `dpop` loss penalizes any drop in the chosen log-probability ([preference/loss.py](/Users/hanmozhang/schoolwork/cmu-agents-project/.venv/lib/python3.12/site-packages/mlx_vlm/trainer/vlm/preference/loss.py)). The smallest published GUI DPO set is still 151 tasks, against our 25–45 pairs.

**Replay** of the user's own demos on new instances is compliant and has a strong robotics precedent: 200 demos generated from 10 human demos reached 79% against 84% for 200 human demos ([MimicGen](https://arxiv.org/abs/2310.17596)). But it copies constants verbatim. Alice's 14:00 applies to afternoon meetings, so a replay built from the wrong source demo stamps the wrong habit, and a task-only checker cannot catch it. Replay also adds no new behaviour and no recovery. It works best as a cheap state generator inside approach 1, where the teacher decides the labels.

**The decision-token loss** is the cheapest change, and TL-Training is its closest low-data evidence: upweighting a tool call's key tokens gave strong results from 1,217 examples ([TL-Training](https://arxiv.org/abs/2412.15495v1)). DFT's probability weighting points the wrong way here. For a decision token at 2 nats (p ≈ 0.13), it is about 7.5× weaker than plain cross-entropy relative to near-certain boilerplate (my calculation from its loss form) ([DFT](https://arxiv.org/html/2508.05629v2)). The effect should be moderate: the weighting amplifies the same 15 states without adding new ones.

**The OPPU warm start** ranks last of the five on preferences but costs almost nothing. OPPU merges a task LoRA trained on other users into the base, then trains a small per-user LoRA (rank 8, q/v, lr 1e-5, 2–3 epochs) ([OPPU](https://arxiv.org/html/2402.04401)). Federated learning finds local fine-tuning from a global model a tough-to-beat baseline ([Cheng et al.](https://arxiv.org/abs/2108.07313v2)). It also finds that such fine-tuning overfits as local epochs grow ([Chen et al.](https://arxiv.org/html/2511.12695v1)). The argument for this approach is a mechanism, not a measurement. On a base that already performs the shared procedure, the user's distinctive tokens are the high-loss ones, so the per-user stage spends its gradient there. Two observations argue against it. In the dry run the other-users adapter C5 did not ground better than C3 (58% vs 61% on other steps). And with only two other users, C5's consensus is the 2-of-3 majority, which is the very "keep the default" behaviour Alice must override. It stays in the plan because it is the leave-one-user-out control the paper needs anyway.

The rejected rows fail for specific reasons. Reverse-KL on-policy distillation updates only tokens the student already samples, and plain on-policy self-distillation failed completely to learn a rare target behaviour until rollouts were guided ([EDGE-OPD](https://arxiv.org/abs/2605.23493)); "click 30 min" is exactly such a rare behaviour. mlx-vlm's GRPO trainer documents no multi-turn rollouts and is tested on tiny models only ([mlx-vlm training docs](https://github.com/Blaizzy/mlx-vlm/blob/main/docs/training.md)). Meta-learning needed 292 tasks in AdaptAgent ([AdaptAgent](https://arxiv.org/html/2411.13451)), and profile-to-LoRA hypernetworks amortize only after about 1,450 users ([P2P](https://arxiv.org/html/2510.16282)). Neither is feasible with three users.

## Conclusion

Every compliant method is a different way of multiplying about fifteen user-specific decisions. They differ in where the extra decisions come from: duplication (upsampling), stated reasons (habit thoughts), contrast with other users (DPO), transfer from other users (warm start), or a teacher that reads the demos and labels states the demos never visited (distillation). Only distillation creates genuinely new decision instances, at new instances and at the off-path states where C3 actually fails, which is why it leads despite its cost. The cheap arms are still worth running first. They share a state-key aligner and an evaluation harness with distillation, and their winning settings become distillation's data format. The constraint also yields a general caution for personalized agents: verifiers that check only the task make self-improvement blind to preferences and bias it toward shorter, habit-skipping trajectories.

The result also sharpens the paper's question of where demonstrated preferences should live. Distillation turns the context arm into the weight arm. If a distilled adapter reaches C1's preference accuracy at C3's cost and task success, the answer is "read preferences from context once, then store them in weights", a stronger claim than either arm makes alone. If the teacher is right on the new states but the student still fails to absorb its labels, that is an informative negative result: at this data size, preferences resist being stored in a LoRA. The paper can report either outcome.

## Five approaches to test, with recipes

### Shared setup: measure decisions, select on the user's own demos

All five recipes share one harness and one state-key aligner, and both should be built first. The harness extends `eval/offline.py`. It reports, on held-out states, decision-token NLL (the quoted label or value in the Thought, plus the typed content), teacher-forced step accuracy split into distinctive and other steps, the default-kept rate on distinctive steps, the repeat-previous-action rate, the wrong-persona leakage rate (outputs another user's value), and parse failures. Online, it reports task success, joint success, steps, loops, prompt tokens per step and seconds per step. Preference adherence is reported for evaluation only. The aligner keys each demo step by page, open dialog or dropdown, focused field, and the set of filled fields, and it aligns a user's demo with other users' demos of the same skill. Approaches 2, 4 and 5 use it directly, and approach 1 uses it to weight distinctive states.

### 1. Context distillation turns the 9/9 teacher into training labels

The hypothesis is that the C1–C3 gap closes when the adapter is trained on demo-conditioned teacher labels at new instances and at the states it visits itself. Hard teacher labels and a DAgger mixture are used instead of reverse-KL sampling, because the target behaviours are rare.

| 4. Thoughts | Re-render each teacher action with approach 4's habit/progress template, so the training format matches. Keep the teacher's raw thought only as a variant. | Template phrasing avoids the teacher artifacts that SDFT's students copied ([SDFT](https://arxiv.org/html/2601.19897)) |
| 5. Train | 70 ground-truth demo samples ×2 as anchors (they protect C3's date pattern and "Save" grounding), plus 300–500 teacher-labelled states. Distinctive and disagreement states get full weight; non-distinctive states are kept only where teacher and student agree, at weight 0.5. Warm-start from the best SFT adapter. | Base recipe, 1–2 epochs; ~640 rows × 5.4 s ≈ 1–2 h |
| 6. Round 2 | β = 0 on fresh instances; relabel, aggregate, retrain. | ~45 min rollouts + ~1 h training |
| 7. Optional soft labels | A custom MLX loop: forward KL over the stored top-20 teacher distribution at temperature 2, plus CE on the anchors. Optionally weight tokens by Δ = log p_teacher(with demos) − log p_base(without), so only demo-driven tokens move. | T = 2 beat T = 1 in prompt distillation ([Kujanpää et al.](https://arxiv.org/html/2412.14964v2)); 6–10 h engineering; the Δ-mask is untested |

The totals are 12–16 engineering hours (plus 6–10 for soft labels) and 3.5–5 Mac-hours per (user, skill). That comes to about 11–15 hours for three personas on calendar and 30–45 hours for all 12 adapters, or about 18 hours with one round of about 250 states. The success criterion: pooled distinctive-step accuracy within about 10 points of C1, while keeping C3's task success, roughly 4,100 tokens per step and 2.4 s per step. Kill the arm if step 0b shows no disagreement, or if round 1 loses other-step accuracy that more anchors cannot restore. The main risk is that the teacher's systematic errors get baked in. The synthetic instructions' explicit dates remove the date-arithmetic error from training. If test instructions keep relative days, though, only the anchors preserve C3's date skill, so adopt STATUS's proposal to add explicit dates to calendar test instructions before recording human demos. As an evaluation-only diagnostic, score the teacher's labels against `recorder/oracle.py` to separate teacher error from distillation loss, and never feed that score back into filtering.

### 2. Contrastive DPO pushes down other users' choices at aligned states

The hypothesis is that explicit negatives at the user's distinctive states push down the specific wrong choices C3 makes. These negatives are other users' values, other users' "move on" actions where this user acts, and the adapter's own repeats. Training is gated to those states and anchored on the chosen likelihood.

| Step | Do this | Settings, cost, guardrails |
|---|---|---|
| 1. Align | Use the shared state-key aligner (Needleman–Wunsch over state keys, with element labels as the tiebreaker) between the user's demo and each other user's demo. Use the same instance in the study variant and the nearest same-skill instance in the deployable variant. | Shared with approach 4 |
| 2. Value negatives | At a distinctive state where another user acts differently (15:00 vs 14:00, "50 min" vs "30 min"), transplant their action into *this user's* screenshot: map the element label to its bbox in this user's element map, re-emit coordinates, re-render the template thought. For `type`, swap only the content. | The prompt is always this user's screenshots and history, never the other user's screen |
| 3. Skip negatives | Where this user acts at state s and the other user has no step there, the rejected response is the other user's next action from s (for example `click "Guests"`), re-expressed in this user's screenshot. | Targets C3's observed skip with no padding |
| 4. On-policy negatives | Run C3 greedy plus 4 samples at T = 0.7 on every train state. Any action that differs from the user's demo action at a distinctive state, and any repeat of the previous action at any state, becomes a rejected response. | ~70 states × 5 × 2.5 s ≈ 15 min |
| 5. Assemble | Dedupe, which gives about 25–45 pairs per (user, skill). Hold out one demo's pairs for leave-one-demo-out selection. Write mlx-vlm preference rows (`prompt`, `chosen`, `rejected`, `images`) with `kind` ∈ {value, skip, onpolicy} metadata. | `train/build_pairs.py`, 4–6 h |
| 6. Train | See the command below. Sweep lr {5e-6, 1e-5, 2e-5} × β {0.1, 0.3} on 2 dev pairs. | ~14–15 s per iteration; 75–135 iterations ≈ 20–35 min, plus loading and mining ≈ 40–55 min per adapter; 45–60 GB peak, so do not run alongside evaluation or recording |
| 7. Anchor fallback | If all-steps accuracy falls below the starting SFT adapter, alternate one epoch of SFT (lr 2e-5) with one epoch of dpop, or write a joint DPO + 0.5·NLL loss with reference log-probs precomputed once. | Joint loss 4–6 h; the anchor was worth 14–18 points in Agentic-DPO ([Agentic-DPO](https://arxiv.org/html/2607.10601v1)) |

```
uv run python -m mlx_vlm.train --train-mode dpo --loss-type dpop --beta 0.1 --delta 50 \
  --model models/UI-TARS-1.5-7B-mlx-bf16 \
  --resume-adapter-file adapters/<best SFT>/adapters.safetensors \
  --data data/pairs/<user>_<skill> --train-type lora --lora-rank 16 --lora-alpha 16 \
  --lora-dropout 0.05 --learning-rate 1e-5 --warmup-steps 10 --batch-size 1 \
  --iters $((3 * N_PAIRS)) --beta2 0.98 --max-seq-length 8192 --grad-checkpoint \
  --steps-per-report 5 --steps-per-save 25
```

`--beta` (the DPO temperature) and `--beta2` (AdamW) are separate options in the installed CLI. The reference model defaults to the base, which subtracts the base model's own bias toward keeping defaults ([DPO config](/Users/hanmozhang/schoolwork/cmu-agents-project/.venv/lib/python3.12/site-packages/mlx_vlm/trainer/vlm/dpo/config.py), [train.py](/Users/hanmozhang/schoolwork/cmu-agents-project/.venv/lib/python3.12/site-packages/mlx_vlm/train.py)). Check the dataset-column flags with `--help`. During training, `chosen_logps` must not fall more than about 1 nat below its starting value. `reward_accuracy` reaching 1.0 within the first epoch means stop. Parse failures must not rise above the starting adapter's rate. Avoid ORPO and SimPO: their per-token mean log-probabilities dilute a one-to-two-token decision across a long shared response, and SimPO is reported to hurt structured output ([SimPO](https://github.com/princeton-nlp/SimPO)). Success is a pooled gain of at least 10 points on distinctive steps over the starting adapter, with lower leakage and skip rates and no loss on other steps. With human demos, expect fewer clean value pairs and more reliance on on-policy negatives.

### 3. An OPPU-style warm start lends the user other users' procedure

The hypothesis is that a shared skill adapter trained on other users' demos supplies procedure and grounding, so that a short, low-learning-rate stage on the user's five demos spends its gradient on the decisions where this user differs.

| Step | Do this | Settings, cost, guardrails |
|---|---|---|
| 1. Stage-1 base | C5(user, skill): the other users' train demos of the same skill. This is leave-one-user-out and deployable for a new user. | 2a. Continued fine-tuning | Resume from C5 on the user's ~70 samples (command below). Pick the epoch by leave-one-demo-out distinctive-step accuracy. | lr 2e-5 (try 5e-5), warmup 10, 2 epochs ≈ 140 iterations ≈ 13 min; zero code; rank must match C5 |
| 2b. Stacked residual (OPPU-exact) | Apply C5 and fuse in fp16/fp32, or keep it unfused in a two-LoRA wrapper; mlx-vlm's `fuse()` adds in the bf16 weight dtype and can round away small deltas. | 3. Strength knob | For 2b, sweep the residual scale s ∈ {1, 1.5, 2} at inference. A larger s amplifies the user's delta, a training-free test of whether skips stem from an under-weighted user signal. | 3 offline evaluations |

| 5. Closed-world variant (optional) | One pooled adapter on all users' demos with a `User: <id>` line and 20% `User: unknown` dropout. The tag is an opaque ID only, never a profile. | ~2.5 h; not deployable for a new user without retraining |

### 4. Habit and progress thoughts give the skipped steps a reason

The hypothesis is that writing the reason ("this user always books 30 min") and the position ("title, date and start are set; next, duration") into the tokens just before the action teaches the adapter when to leave the default path and where it is.

| Step | Do this | Settings, cost, guardrails |
|---|---|---|
| 1. Mine habits (new `train/habits.py`) | For each step of the user's demos, using demos only, compute three flags. *Distinctive*: the action key appears in no other user's aligned step (the `critical_map` rule from `eval/summarize.py`, keyed by state instead of instance). *Habit*: the same action or value recurs at that state in ≥3 of the user's 5 demos, or consistently within an instruction-keyword split such as morning vs afternoon. *Slot*: the typed text matches an instruction entity (attendee, date, topic), and a slot is never a habit. Read the field's current on-screen value (for example "60 min") from the frame's element map. | Never reads `apps/personas.py`; 2–3 h |
| 2. Templates (`habit_thought` in `agent/thoughts.py`) | Distinctive step with a default deviation: `Title, date and 14:00 start are set. Duration shows 60 min; this user always books 30 min, so I'll click "30 min".` Distinctive value: `This user starts afternoon meetings at 14:00, so I'll type "14:00" into the Start time field.` Keep-default step, where the user leaves a field that others change: `Duration already shows 60 min, which this user keeps; next, I'll click "Guests".` Non-distinctive step: `Done: title, date. Next, I'll click "Guests".` | ≤ ~30 tokens; cite only current and past screens and the demos' regularities, never later steps; 1–2 h |
| 3. Mixed formats | Keep 25% of rows with the plain template. | OpenCUA's mixture beat single-format training ([OpenCUA](https://arxiv.org/html/2508.09123v3)) |
| 4. Upsample | Duplicate distinctive-step rows ×3 in `train.jsonl` (a `build_sft.py` flag), which gives ~100 rows. | No code beyond the flag |
| 5. Train | Base recipe. | ~400 iterations ≈ 36 min |
| 6. Inference | Unchanged. The agent writes its own thoughts and sees its own previous thoughts, so training and inference stay in parity. Optional variant: action-only history in both training and inference. | OpenCUA found no gain from thought history ([OpenCUA](https://arxiv.org/html/2508.09123v3)) |
| 7. Ablation (night 1) | (a) template + upsampling; (b) habit thoughts; (c) habit + progress; (d) habit + progress + upsampling. | 4 × ~35 min per dev pair |

If an LLM rewriter is preferred to the deterministic miner, the compliant version is Lampinen-style global augmentation. The C1 teacher sees all five demos and rewrites each of the 70 thoughts to state the cross-demo regularity behind the gold action, while the action stays fixed ([Lampinen et al.](https://arxiv.org/html/2505.00661)). That takes about 70 teacher calls, or 5–8 minutes. Success means the default-kept rate on distinctive steps approaches zero, the repeat-previous rate falls, and pooled distinctive-step accuracy rises by at least 10 points over C3. The specific risk is over-application: an adapter that has learned "this user always books 30 min" may override an instruction that asks for 15 minutes. Measure that on override tasks. Human demos will also show habits recurring less often than the oracle demos do, so log the miner's coverage per user.

### 5. Decision-token weights move the gradient into the Thought

The hypothesis is that concentrating the loss on the tokens that commit the action brings decision-token NLL down from 2+ nats without overfitting the boilerplate.

| Step | Do this | Settings, cost, guardrails |
|---|---|---|
| 1. Mark spans | In `build_sft.py`, emit per-row character spans: the quoted label or value inside the Thought, the habit phrase (from approach 4), the action-type token, the coordinate digits, and the first two tokens of typed content. | ~1 h |
| 2. Weights | Extend `train/weighted_sft.py` to map spans to token positions by tokenizing the assistant text with offsets. Weights: boilerplate 1; Thought label/value 4; habit phrase 2; action type 2; coordinate hundreds/tens/units 3/2/1; first typed tokens 4. Multiply decision weights by 2 at distinctive steps when not upsampling. Keep the patch's normalization by Σw. | Check digit tokenization with `tokenizer.tokenize("(523,311)")`; 1–2 h |
| 3. Arms | (a) current A5 (Action span ×4), as a reference; (b) decision-span weights; (c) focal weighting (1 − p)², detached, over all completion tokens. Never DFT's ×p. | ~25 min each |
| 4. Optional unlikelihood | At distinctive steps, add 0.5 · −log(1 − p(t_neg)) at the first divergent token of the other user's aligned action, using the token from approach 2's aligner. | A reference-free, DPO-lite contrast; 2–3 h |
| 5. Sweep | Decision weight ∈ {2, 4, 8} on 2 dev pairs. | The weights are starting points, not published values |

Run it with the same CLI as the base recipe: `uv run python -m train.weighted_sft --model … --data … [base recipe flags] --beta2 0.98`. A reasonable target is held-out decision-token NLL below about 0.7 nats (p > 0.5) at distinctive states, with distinctive-step accuracy up and other-step accuracy and parse failures unchanged; that threshold is my suggestion, not a published one. Concentrating the gradient on a few tokens raises per-step gradient variance, the same mechanism suspected behind the lr ≥ 1e-4 divergence, so this arm should always run with the lower β2 and the finite-checked clip. GUI-SD's digit-significance weighting is the nearest published precedent for weighting coordinates ([GUI-SD](https://arxiv.org/abs/2605.00642)), but no clean SFT-only ablation of decision-token weighting exists for GUI agents. That makes this the experiment that tells us how much of C3's gap was just loss accounting.
